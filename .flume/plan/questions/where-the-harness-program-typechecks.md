# Where does the harness program's typecheck run?

Driver: intent invariant 8 names "the compiler's own errors" as a channel the author receives through the verbs it runs. But emit runs the program under Node's type stripping and nothing runs `tsc`, so a wrong field, a removed constant or a `never`-typed field passes emit and check. An adopter's standing type error (`registration: []` on an embedded kind) went unseen, and the remedy-naming errors SDK-TYPE-ERRORS-NAME-THEIR-REMEDY shipped reach no one. `specs/model/pipeline.md`, "Emit", carries no typecheck step, and `specs/model/authoring.md`, "The SDK", says only "typed at the keystroke".

What the corpus already decides: `check` is out, because "checking never needs Node" (authoring.md, "The SDK"). An `install`-scaffolded `tsconfig` plus script is exposure, not delivery ("exposed is not delivered", invariant 8). That leaves emit, the one verb that runs the program.

What it does not decide: (a) whether emit refuses on a type error (like the "Refusing" list) or reports it as counsel and continues, and (b) which compiler runs. `typescript` is only a devDependency of `@dtmd/temper` today (sdk/package.json), so emit would need either the program's own `typescript` or a new runtime dependency. Recommendation: emit typechecks with the program's own resolved `typescript` and refuses on error, naming the compiler's diagnostics, with a loud refusal when none resolves. A type error is an authored shape the SDK declared wrong, and refusing is how emit already treats such shapes. Strongest objection: tsc's cost on every emit, and a refusal that depends on a compiler version the lock does not pin. Seen by an inbox record from an SDK adopter (2026-11-25).
